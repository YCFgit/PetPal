# 宠伴上门 MVP 产品需求与验收基线

> 状态：评审草案。本文将现有方案细化为首期可验收范围；经营地、交易结构、价格、取消政策和合规结论仍须由业务负责人确认。

## 1. 目标与边界

验证一个服务片区内的“用户下单并付款 → 运营派单 → 喂养师履约 → 用户反馈/售后 → 财务对账”闭环。首期允许人工运营兜底，不追求自动调度、全国化或复杂资金产品。

### 范围优先级

| 优先级 | 范围 | 验收结果 |
| --- | --- | --- |
| P0 | 用户登录、宠物/地址、服务报价、预约下单、支付核验、取消/退款、评价 | 仅本人能访问自己的资料和订单；金额以后端报价为准；支付通知重放不重复入账；完成订单可评价且不重复 |
| P0 | 喂养师申请/审核、人工派单、接单/拒单、签到/服务记录/签退 | 未审核通过者不能接单；只能访问有效分配给自己的订单 |
| P0 | 后台订单、派单/改派、退款审批、售后工单、审计 | 高风险操作有权限、原因、前后状态和操作者记录 |
| P0 | 时段供给校验、订单超时、通知失败重试、财务对账 | 并发下不超卖；异步失败可重试并可人工恢复 |
| P0 | 基础运营及财务报表 | 提供订单、履约、退款、应结/实付与差异记录；口径可追溯 |
| 暂缓 | 优惠券与复杂营销报表 | 原方案中属于后续能力，不阻断首期主链路 |
| 暂缓 | 自动派单、钱包/储值、自动分账/提现、即时通讯、独立 App | 未经业务和合规评审不得纳入首期 |

## 2. 首期端形态建议

建议先采用“用户小程序 + 喂养师小程序角色模式 + PC 管理后台”，复用小程序代码与服务端 API；用服务端角色授权区分用户和喂养师功能。此决定以喂养师使用微信小程序可满足定位、上传、通知为前提，需在方案评审确认。如果审核规则、使用体验或运营要求不支持，再拆独立喂养师端，不在首期预先建设两套客户端。

## 3. 关键业务规则（评审后冻结）

1. 用户提交报价请求后，服务端根据有效服务/价格版本、区域、时长、宠物数量及附加项计算价格；客户端金额仅用于展示。
2. 建单时锁定价格、服务条款、宠物照护说明和预约时段快照；支付时限建议 15 分钟，业务方可配置。到期先禁止新预支付请求，并通过渠道查单、关单裁决在途支付。确认未支付且已关闭后才能释放预约名额；结果未知时保留占位并告警。已释放名额后发现真实支付成功时保留支付事实，按已批准的退款/人工核查策略处理，不可悄悄恢复已释放时段。
3. 下单在同一数据库事务内原子占用时段容量并创建待支付订单，失败整体回滚。支付成功后转为待派单；派单失败不改变已支付事实，进入运营告警和人工处理。首期一单仅包含一次上门，连续多日/多次服务拆成独立订单，不隐含周期预约。
4. MVP 由运营人工派单。服务人员接受前不能查看精确门牌、入户凭证；接受后按履约时窗授权，签退/取消后撤销访问权。
5. 服务完成后先进入待审核/待确认；若用户在 24 小时内未反馈，自动完成仅可在业务协议确认后启用，否则由运营核验完成。售后中的订单不可结算。
6. 退款与结算以支付渠道结果和追加式账务流水为准；每笔人工调整必须有理由、审批人和审计记录。若实际交易结构、支付及财税核验允许，首期可线下结算，但须记录应付、实付、渠道凭证和对账结果；不能因人工打款而绕过合规核验。部分退款不等于整单取消或全额退款，已结算订单发生售后时需冻结后续付款并以调整流水处理追偿/抵扣。
7. 退款时限、取消梯度、爽约费、服务人员报酬及结算周期尚未给定，属于上线前业务阻断项，不能由研发自行设定。

## 4. 非功能验收

- 权限：用户、喂养师、客服、审核、财务、管理员按资源归属和数据范围鉴权；所有敏感操作留痕。
- 一致性：订单创建、名额占用、接单、支付、退款均幂等；并发竞争不超卖、不重复分配、不重复记账。
- 隐私：精确地址和入户凭证分开存储；凭证按订单短时授权、加密和访问审计；影像私有存储并设定保留期限。
- 可恢复：支付通知丢失可主动查单；异步任务可重试；数据库及对象元数据完成备份恢复演练。
- 上线阻断：支付/退款金额错误、严重越权、凭证明文暴露、核心数据不能恢复、必要主体/平台能力/协议未核验、重大事件无人值守。

## 5. 评审前需业务确认

| 决策 | 默认建议 | 负责人/状态 |
| --- | --- | --- |
| 首发城市/片区、营业主体 | 明确一个城市及 1–3 个相邻片区 | 业务负责人待确认 |
| 喂养师端形态 | 同一小程序多角色 | 产品/运营待确认 |
| 服务项目与服务时长 | 先选 1–2 个低风险标准服务 | 运营待确认 |
| 预约时段容量/服务半径 | 按喂养师有效可用量与路程缓冲配置 | 运营待确认 |
| 未支付时限、取消/改约政策 | 后台可配置、订单保存规则快照 | 业务/法务待确认 |
| 用户确认与自动完成规则 | 默认需人工/用户确认，不自动结算 | 业务/法务待确认 |
| 支付主体、退款与服务人员结算 | 先验证官方能力；线下结算也需留账 | 财务/专业顾问待确认 |
| 定位、影像、凭证留存期限 | 最小化且按用途/争议要求分别设定 | 隐私/法务待确认 |

## 6. 验收场景

- 同一幂等键重复建单返回同一结果；不同请求抢最后一个名额只允许一个成功。
- 未支付订单过期释放名额；支付成功通知延迟或重复不造成错单/重复账务。
- 两名喂养师竞争同一单只能有一名有效接单人；改派保留历史且撤销前任访问权限。
- 用户、喂养师尝试访问他人订单、地址、影像均被拒绝并记录安全事件。
- 退款失败可重试/人工处置；账务差异有报表、责任人和关闭证据。
- 图片上传中断可重试，未确认入库的对象不可被用户读取，过期对象可清理。
- 重大宠物/入户事件可升级到值班负责人，售后未结案前不可正常结算。
